# PERF-DIAG-001 — 研究装配（Research Run Assembly）性能诊断与方案对比

- **状态**：诊断完成（**只读，未改任何产品代码**）
- **日期**：2026-09-12
- **触发**：用户反馈「项目中的分析研究过于慢，应该是数据过于多」
- **结论先行**：慢的**不是分析算法**（5 类分析合计 11.9s），而是**把数据从跨境 TiDB 搬进 Node**。
  三个可落地杠杆已受控实测：**压缩协议 4.7~6.0× · 列裁剪 3.3× · 有界并发 2.7~3.2×**，
  复合预期 **529.7s → 25~55s**；再叠加装配结果本地快照可到稳态 **3~8s**。

---

## A. 执行摘要

| 事实 | 证据 |
|---|---|
| 研究 Run 的耗时 **98% 在装配**，不在计算 | v2 单次运行：装配 **529,740ms** vs 5 类分析合计 **11,871ms** |
| 装配慢的性质是**数据搬运**，不是 SQL 慢 | 单页 9 万行纯搬运 169s；`EXPLAIN` 走既有唯一键，无全表扫描 |
| 不是延迟受限（RTT 不是主因） | RTT≈208ms × 约 48 次往返 ≈ 10s，仅占 529.7s 的 **2%** |
| 是**吞吐受限**，且吞吐可被并发放大 | 1→3→6 连接：5,666 → 15,458 → 18,357 rows/s |
| 两个「白送」的浪费 | `SELECT *` 多搬 9 列（3.3×）；连接池未开 MySQL 压缩协议（4.7~6.0×） |

  唯一变量 = 待测项。

## C. 成本构成（实测，单连接 / 无压缩 / 全列）

| 步骤 | 行数 | 耗时 | 单行成本 |
|---|---|---|---|
| 事件页 `listEventsPage` | 2,000 | 888ms | 0.44ms |
| `prefix` rd=−20..0 | 42,000 | **62,123ms** | 1.48ms |
| `path` rd=1..20 | 40,000 | **96,575ms** | **2.41ms** ← 单行最贵 |
| `outcome` h=5/10/20 | 6,000 | 9,512ms | 1.59ms |
| **单页合计** | **90,000** | **169,098ms** | 1.88ms |

**并发因子反推**：12 页 × 169.1s = 2,029s，而生产实测 529.7s ⇒ **3.83×**，
与「`Promise.all` 同时发 3 张表的批量查询」及并发标定（N=3 → 2.73×）方向一致。

> 结论：**装配成本 ≈ 行数 × 单行成本 ÷ 并发度**。三个因子就是三个杠杆，没有第四个。

## D. 为什么 `path` 最贵、`prefix` 次之

由 `drizzle/schema.ts` 实测列宽（研究真正需要的列用粗体）：

| 表 | 总列数 | 研究需要的列 | 多搬的列 |
|---|---|---|---|
| `prefix` | 13 | **eventId, relativeDay, close, volume**（4） | `id` / `symbol` / `tradeDate` / `open` / `high` / `low` / `amount` / `createdAt` |
| `path` | 15 | **eventId, relativeDay, highFromEventClose, lowFromEventClose, closeFromEventClose, pullbackFromEventHigh**（6） | `id` / `symbol` / `tradeDate` / `volumeRatio` / `isBreakout` / `breakoutPrice` / `daysToBreakout` / `createdAt` |
| `outcome` | 10 | **eventId, horizon, + 5 个指标**（7） | `id` / `createdAt` |

`path` 单行最贵正是因为它把 `symbol`(varchar32) / `tradeDate`(date) / `isBreakout` / `breakoutPrice` /
`daysToBreakout` / `volumeRatio` 全部搬了过来，而这些在研究侧**一次都没被读取**
（`variables.ts` 只取 4 个 path 衍生列 + `outcome` 的 3 个聚合列与 2 个 flag 列）。

> 需要**申请了多少列**由 `variables.ts` 的变量目录决定：最重的特征是 `pre_volatility_20d`
> （prefix rd∈[−20,0]，21 天），最重的结果是 `future_return_{h}d`（path rd∈[1,20]，20 天）。
> 因此一次「全变量」研究的装配确实等价于把整个版本的窗口数据搬一遍。

## E. 三个杠杆 —— 受控 A/B 实测

### E.1 MySQL 压缩协议（`compress: true`）—— 单条最大杠杆

| 路径 | 无压缩 | 压缩 | 倍数 |
|---|---|---|---|
| mysql2 `query()`（text protocol） | 68,126ms（64,696 / 71,555） | 14,626ms（13,119 / 16,132） | **4.66×** |
| **drizzle `select()`（prepared statement，即生产真实路径）** | 60,646ms（56,470 / 64,822） | 10,115ms（**4,650** / 15,579） | **6.00×**（区间 4.2~13.0×） |

- **两者协议不同必须分别验证**：本项已在真实代码路径（prepared statement）上确认生效，
  不是 text protocol 的假象。
- ⚠️ **诚实标注方差**：压缩组两次为 4,650ms / 15,579ms（3.4× 波动），说明跨境链路本身在波动；
  **方向与量级稳健（稳定 ≥4×），精确倍数不稳定**。方案预算按保守 **4×** 取值。

### E.2 列裁剪

| 对照 | 耗时 | 倍数 |
|---|---|---|
| 全 13 列 | 68,126ms | 1.00× |
| 裁剪到 4 列（`eventId, relativeDay, close, volume`） | 20,812ms（20,551 / 21,073） | **3.27×** |
| 裁剪到 3 列（再去 `volume`） | 17,900ms | 3.81× |

### E.3 复合效应

| 组合 | 耗时 | 倍数 |
|---|---|---|
| 无压缩 + 全列 | 68,126ms | 1.00× |
| **压缩 + 裁剪** | **5,762ms**（5,262 / 6,261） | **11.82×** |

复合**接近相乘**（4.66 × 3.27 = 15.2，实测 11.8，存在轻度次线性）。方案预算按保守 **10×** 取值。

### E.4 有界并发（压缩 + 裁剪后）

| 并发连接数 | 耗时 | 吞吐 |
|---|---|---|
| 1 | 7,413ms | 5,666 rows/s |
| 3 | 2,717ms | 15,458 rows/s（**2.73×**） |
| 6 | 2,288ms | 18,357 rows/s（**3.24×**） |

并发收益在 6 连接后明显收敛（3→6 仅 +19%），说明已接近链路饱和 ⇒ **不建议无脑堆并发**。

### E.5 压缩对**小查询**的副作用（生产池是全站共享，必须验）

| 查询 | 无压缩 | 压缩 | 比值 |
|---|---|---|---|
| `COUNT(*)` | 242.1ms | 241.3ms | **1.00×（中性）** |
| `LIMIT 500`（4 列） | 376.3ms | 290.4ms | **1.30×（更快）** |

⇒ **无反作用**。`compress: true` 可以安全地开在全局连接池上。

## F. 已排除的方案（附实测否证依据）

| 方案 | 否证证据 |
|---|---|
| **keyset 流式分页替代 `IN (...)`** | 实测 60,000 行 / 10,887ms = **5,511 rows/s**，与单连接基线 5,666 rows/s **持平** ⇒ 无收益。放弃重构。 |
| **加大分页**（2000 → 8000 事件） | 4× 数据 → 4.04× 时间（62.1s → 250.9s），**严格线性** ⇒ 不改变单位成本。 |
| **覆盖索引**（含 `close`/`volume` 免表回查） | 未实测收益；`ALTER TABLE ADD INDEX` 在 50 万行 × 跨境链路上代价高，且属 schema 变更（需走 migration 纪律）。**收益未证、成本确定** ⇒ 不优先。 |
| **把 quantile / event-study 等改为 SQL 聚合下推** | 5 类分析是**通用纯函数**（`analyses/*.ts`），下推会把口径拆成 5 套 SQL，违反「口径唯一」，**口径风险极高** ⇒ 不做。 |
| **`worker_threads`** | 项目已有明确禁令（连板状态须单线程串行推进）；且本问题是 IO 受限，多线程无益。 |

## G. 方案对比

### 方案 A —— 不动架构，只优化取数（**推荐先做**）

三处改动：① 连接池开 `compress: true`；② `DbDatasetDataReader` 四条批量/分页路径列裁剪；
③ 装配编排把**页间流水**引入（现有仅 3 表并行，页间是串行的），走既有
`server/datasetRegistry/concurrency.ts` 原语。

| 项 | 评估 |
|---|---|
| 预期收益 | 529.7s → **25~55s**（复合 10×，再乘页间并发 2.5~3×；取保守区间） |
| v1（1,130 事件） | 现约 10s → **亚秒~2s** |
| 改口径？ | **否**。只改「怎么取」，不改「取什么」、不改任何判定/筛选/统计 |
| 改数据？ | **否**。纯只读路径 |
| 新增依赖 | 无（`compress` 是 mysql2 内置选项） |
| 风险 | **低**。主要风险是「裁剪清单漏列 → 特征静默变 null」，须用测试锁死（见 §H.2） |
| 工作量 | 小（4~6 文件） |

### 方案 B —— 叠加「装配结果本地快照」（**可选第二步**）

沿用项目既有 `.cache/` 模式（先例：`stockPriceIndex.ts` 的 `stock-price-day-index.json` 4MB、
`leaderCandidateBacktestSnapshot.ts` 的 6h 快照）。把**装配产出**（每个事件的特征/结果/维度值，
约 23,978 样本 × ~110 值）按 `(datasetVersionId, dateRange, readerSchemaVersion)` 落本地。

| 项 | 评估 |
|---|---|
| 预期收益 | 稳态 **3~8s**（含本地反序列化 + 对象重建；1.07M 行退化为 2.4 万样本） |
| 首次 | 仍需付一次方案 A 优化后的全量（~25~55s），之后命中 |
| 命中率 | 研究是**迭代行为**（同版本反复换变量/视界跑）⇒ 近似 100% |
| 磁盘 | 约 21MB（紧凑二进制）~ 80MB（JSON） |
| 风险 | **中**。新增一层缓存，必须带 provenance 失效；⚠️ **数据集版本「原地重建」陷阱**（见 §H.3） |
| 工作量 | 中（新模块 + 单测 + 失效路径） |

### 方案 C —— 全量镜像到本地 MySQL/TiDB Lite

需用户安装并维护本地数据库服务，运维成本远超收益 ⇒ **不推荐**。

## H. 若批准实施的关键要点（风险前置）

### H.1 `compress: true` 的作用域
作用于 `server/db.ts` 的**全站共享池**。已实测对小查询中性或更快（§E.5），但实施后仍应对
组合回测（龙头候选）与行情同步页做一次回归计时，确认无回退。

### H.2 🔴 列裁剪最危险的失败模式：**静默变 null**
裁剪的是**传输列**，domain 形状不变（未取列填 `null`）。若裁剪清单漏掉某变量需要的列，
`resolve` 会**静默返回 null**（`variables.ts` 里是 `?? null`），不报错、不抛异常 ⇒ 研究结论会
在「样本量骤降」或「特征全空」上失真，而**没有任何告警**。

**必须的防护**：在变量定义上显式声明所需原始字段（如 `prefixFields: ["close","volume"]`），
由读取层**计算并集**得出裁剪清单，并加一条测试断言
「每个变量声明的字段 ⊆ 物理表可用列」，且「裁剪清单 ⊇ 目录所需并集」。
这与项目「写错就读不到」的既有 PIT 设计哲学一致。

### H.3 🔴 方案 B 的失效判据：**不能靠版本号**
`DATASET-LIFECYCLE-001` 已把「重建 = 从零」落地：`runner.execute` 会在构建前
`purgeVersionRows(versionId)` 并**复用同一个 `datasetVersionId`**。
⇒ 快照失效**必须**依据 `dataset_version.updatedAt`（或 `completedAt`）+ `status` + `totalEvents`
+ 各表真实行数 + `readerSchemaVersion`，**不能**只比对 versionId（否则重建后仍命中旧快照，
静默读到已 purge 的旧数据）。

### H.4 并发纪律
并发原语**必须**复用 `server/datasetRegistry/concurrency.ts`（项目明确禁止别处重写）；
连接池经 `DB_POOL_SIZE` 调整，当前默认 10，建议提到 **16~24**（6 连接已近饱和，留余量给常规查询）。

## K. 边界与诚实标注

- 本报告**只诊断、未实施**；所有倍数均为**真实 TiDB 实测**，非估算。
- 跨境链路存在**时间漂移**（同一查询两轮差异可达 30%+），故所有结论均以**交替 A/B + 两轮**取值，
  并对压缩倍数给出 4.2~13.0× 的区间而非单点。
- 方案 A 的 **25~55s** 与方案 B 的 **3~8s** 是**基于实测单行成本与并发标定的外推**，
  **尚未端到端验证**；实施后必须用 `scripts/` 下的端到端脚本复核（与既有
  `verifyResearchEngine.mts` 的耗时口径对齐）。
- 本报告**不改变**任何「口径唯一权威」：不对 Dataset 构建、判定、筛选逻辑提出任何修改。
