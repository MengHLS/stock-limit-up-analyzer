## 4. 🔴 最重要的结论：**推翻了上一轮的根因假设**

| | 上一轮（DATASET-REBUILD-EXEC-001）假设 | **本轮实测** |
|---|---|---|
| 根因 | 连接/传输层**瞬时**重置（旁证：验收脚本撞过 `ECONNRESET`） | ❌ **不成立** —— 同一断点**连续 5 次**以同一语句失败、**断点零前移** |
| 推论 | 多次续跑可累积推进 | ❌ **错误** —— 重试**永远不会**成功 |
| 修正后的根因 | — | 🔴 **确定性、数据/批次相关的写入失败**（在 `chunk 2461` 处恒定复现） |

**排除「基础设施瞬时故障」的证据**：
1. 同一批次连续 5 次失败，**断点一字未前移**；
2. 每轮 ~30 s 即失败 ⇒ 是**首个待写批次**就失败，不是长跑后被掐断；
3. `failedRows = 0` ⇒ 行级无失败，是**语句级**被拒。

**仍未知的是「确切错误码」** —— 因为 `dataset_build_job.errorMessage` 长 16,000 字符**全部是 SQL 文本**，**不含 `errno` / `sqlState` / `cause.code`**（已在上一轮登记为平台缺口）。**这是唯一挡住定性的信息。**

**候选根因（按可能性排序，均未被证实）**：
1. **`ER_NET_PACKET_TOO_LARGE`** —— 同一批次尺寸恒定 ⇒ 天然**确定性**复现；且 v9（`prefix`）与本轮（`post`）失败**同为大 INSERT**。与「v5–v8 曾成功」不矛盾（上游数据随日期增长使单批变大，或对端 `max_allowed_packet` 被调整）。
2. **某一列的值超出列定义/长度**（如 `VARCHAR` 截断、数值越界）—— 该日某只股票的数据异常。
3. **`ER_LOCK_WAIT_TIMEOUT` / 死锁** —— 但 5 次均在 ~30 s 内失败，与锁等待超时（通常数十秒且会变化）**不太吻合**。
