## 1. P0 正确性问题

### BT-260926-01 每只证券只交易一次，年度交易数逐年下降

**现象**

- 3F TopN 回测的年度交易数逐年快速下降。
- Dataset v5 每年仍有大量首板事件，但执行侧没有产生对应交易。
- 信号数几乎等于“每只证券在本数据集中的第一次事件数”。

**根因**

- 数据集原始行是事件级，包含 `eventId` 和 `relativeDay`。
- 旧执行面板以 `(securityId, tradeDate)` 去重，把同一证券的多个事件窗口合并成一条长序列。
- Core 通过 `SERIES_START` 锚定后只识别该长序列的第一个事件。
- Core 再以 `satisfiedToday && !satisfiedBefore` 产生信号，因此同一证券的后续事件不会形成新交易。

**影响**

- 旧回测实际上是“每只证券只交易一次”的退化策略。
- 2019 年集中消耗存量证券，后续年份只剩新增证券，因此交易数递减。
- 该问题会直接改变年度表现、胜率、回撤和换手。

**修复**

- 执行面板使用 `securityId::event:<eventId>` 作为事件级身份，见 `server/eventIdentity.ts`。
- 同一证券的每个事件窗口保留为独立 bars 序列，见 `server/runWorkbenchAssembly/datasetFromRegistry.ts`。
- 3F 留档中已能看到同一证券的多次成交。

**当前状态**

- 工作区代码已修复。
- `v1.4.0` 报告已经显示事件级结果。
- 仍需在 `v1.6.0` 固定仓位版本上完成 N3/N5 成对重跑。

### BT-260926-02 3F TopN 止损从未生效

**现象**

- 页面中几乎看不到 `止损（5.00%）`。
- 用户怀疑止损规则没有被回测引擎执行。

**根因**

- 3F 策略文档当时只声明了 `TIME_EXIT`。
- 闭环装配读取不到 `STOP_LOSS`，因此 `exitPolicy.stopLossRatio` 为 `null`。
- 引擎本身支持止损，但策略从未把止损配置传入执行层。

**修复**

- 3F TopN 补充 `STOP_LOSS = 5%` 声明。
- 策略版本升至 `v1.1.0` 并完成真实重跑。
- 页面只展示带止损口径的新版本留档，旧 `v1.0.0` 结果不再套用新文案。

**验证**

- Top5 实际触发止损 15 笔。
- Top3 实际触发止损 11 笔。
- `exitPolicy` 留档为 `{ stopLossRatio: 0.05, takeProfitRatio: null, maxHoldingDays: 5 }`。

### BT-260926-03 买入日止损与 T+1 冻结死区

**用户复现**

- `002719` 在买入日盘中已经跌破止损线。
- 下一交易日没有重新触发止损。
- 最终第三个交易日才卖出。

**根因**

- 买入日份额受 T+1 冻结，不能当日卖出。
- 旧实现没有跨日保留“止损已触发但卖单尚未完成”的状态。
- 下一交易日重新判断时，部分路径没有继承已触发止损。

**修复**

- 止损触发状态按持仓跨日保留。
- 卖单因跌停、停牌等原因未成交时，后续候选退出或时间退出继续继承止损原因。
- 真正清仓后删除状态，避免污染下一次同事件持仓。

**验证**

- `002719.SZ@2019-01-21` 的修正结果为 2019-01-29 买入、2019-01-30 止损卖出，`holdingPeriod = 2`。
- 旧结果的卖出日为 2019-01-31，`holdingPeriod = 3`。

### BT-260926-04 止损原因发生前视覆盖

**用户复现**

- `603348` 的一笔交易最终盈利 `+7.89%`，但退出原因显示为 `止损（5.00%）`。

**根因**

- 为保留止损原因，旧实现曾在处理当日到期订单前，用当日完整 K 线的 `low` 预判止损。
- 该预判使用了当时尚未发生的盘中最低价。
- 如果当日开盘普通候选退出先成交，收盘后的止损预判仍覆盖原退出原因，形成前视和错误标签。

**修复原则**

- 先执行到期订单，再判断尚未被卖出的持仓是否触发止损或止盈。
- 只有实际发出了止损卖单而未成交时，才跨日保留止损原因。
- 已在前置订单中清仓的持仓，不得被之后的盘中低点反向标记为止损。

**当前状态**

- 当前工作区执行顺序已经调整。
- 尚未看到专门针对 `603348` 该类场景的独立回归测试。
- 需要补一条“开盘普通退出先成交、盘中稍后跌破止损线不得覆盖原因”的测试。

### BT-260926-05 组合持仓上限错误

**现象**

- N3/N5 实际最大同时持仓达到 12/20。
- 回测后期交易快速减少。

**根因**

- 组合容量曾写成 `maxPositions = topN * 4`。
- `TopN` 是每日横截面候选数，不是组合最大持仓数。
- 早期未平仓持仓占满容量后，后续买入持续被 `MAX_POSITIONS_REACHED` 拦截。

**真实留档证据**

- N3：峰值持仓 `12/12`，因持仓上限跳过 `3837` 次买入。
- N5：峰值持仓 `20/20`，因持仓上限跳过 `6973` 次买入。
- 旧结果在 2023 年以后基本没有新成交。

**修复**

- N3/N5 最大同时持仓统一为 5。
- 单日最多新建仓：N3 为 2，N5 为 3。
- 执行结果显式记录 `MAX_DAILY_BUYS_REACHED`。

### BT-260926-06 执行日无行情导致持仓悬挂

**现象**

- 卖出订单的执行日没有该证券行情。
- 仓位长期无法退出，个别持仓从 2019 年悬挂到期末。
- 悬挂仓位继续占用组合容量。

**根因**

- 卖出订单固定使用下一交易日开盘执行。
- 若数据集事件窗口在下一交易日没有该证券行，卖单会被拒。
- 后续没有可用行情行重试，最终只能按期末持仓计价。

**修复**

- 当下一交易日确定没有该事件行情时，使用最后可得收盘价强制清算。
- 清算仍执行卖出滑点、费用和组合约束，并写入明确退出原因。
- 增加“事件窗口最后一行跌停且次日无行情”的回归测试。

### BT-260926-09 长算后写大结果失败

**现象**

- 回测计算完成，页面也能看到结果。
- `closed_loop_backtest_run` 没有新行。
- 长算后写库出现 `ECONNRESET` / `EPIPE`，极端情况下进程退出。

**根因**

- 数据库池空闲回收阈值大于实测链路空闲窗口。
- 长算期间没有 SQL 往返，连接变成半开状态。
- mysql2 对部分致命错误会二次触发 `error`，缺少池连接错误兜底时会成为 unhandled error。

**修复**

- 收紧池 `idleTimeout`。
- 保留并扩大留档重试预算。
- 给池连接增加致命错误日志兜底，保证重试路径有机会继续执行。

**验证**

- 失败形态和重试预算已有单测与留档证据。
- 3F 结果导入和后续留档写入已验证成功。

## 3. 尚未关闭的口径问题

### BT-260926-10 执行回测与研究侧持有期不等价

**问题**

- 研究侧主口径是 `T+6 Open -> T+10 Close`。
- 当前 Core 对每个事件只在首个有效日出一次信号。
- 执行侧使用 `hold-while-selected`，事件在 T+6 后不再入选，常在约两个交易日后退出。
- `TIME_EXIT = 5` 当前只是上限，不是常态持有期。

**影响**

- 当前回测不能被表述为研究结论的直接执行验证。
- 即使事件身份已经修复，执行收益也不能直接与研究侧的固定持有期收益对比。

**待裁定**

- 若要保持研究口径，Core 需要支持同一事件在持有期内持续触发或显式维持 desired 状态。
- 若接受执行变体，则报告必须明确标注这是短持有期策略，不能用于验证原研究主结论。
