# 龙头候选页「加载不出来」故障诊断（2026-09-19）

> 报告编号（本次工作）：**`9bv`**（未占用；如需登记到 ROADMAP 由用户决定）
> 性质：**只读诊断 + 方案**。本轮**零源码改动**（`server/**`、`client/**` 零 diff）、**零库写入**、
> **未启动/重启任何服务**。新增仅 2 个只读探针（`docs/evidence/_probe_lc_slowpath.mjs`、
> `_probe_db_tcp.mjs`）与本文档。

---

## 0. 结论摘要

用户报「复盘分析 → **龙头候选**加载不出来」。实测确认：页面上两个**重端点**返回 **HTTP 500**，
而它们**都不是因为查询太重、也不是因为网络慢** —— 用全新连接跑**同一条全区间查询，22.8 秒即成功**。

⇒ **根因是 dev server 进程内的 MySQL 连接池已损坏（残留死连接），不是数据问题、不是网络问题。**
⇒ 最快恢复手段：**重启 dev server**（重建连接池），冷算一次成功后即写回磁盘快照，之后 6 小时秒开。

---

## 1. 现象与复现（真实 HTTP）

对运行中的 dev server（`127.0.0.1:3000`，进程 pid 35036，**启动时间 22:01:30**）直接打 tRPC：

| 端点 | 时间 | 结果 |
|---|---|---|
| `sentiment.getLeaderCandidates`（轻） | 22:12 | **200**，58,456 ms（冷算未命中） |
| 同上（缓存热后连打两次） | 22:12 | 200 / **38 ms**、**6 ms** |
| `sentiment.getLeaderCandidateHistoryPage`（重） | 22:12 | **500**，169,684 ms —— `Connection lost: The server closed the connection.`，栈顶 `loadBacktestPriceRows`（`server/db.ts:2316`） |
| 同上，复测 | 22:15 | **500**，119,878 ms —— `connect ETIMEDOUT`（建连阶段，20s × 3 次尝试） |
| `sentiment.getLeaderCandidates` 再冷算 | 22:17 | **200**，11,641 ms |

**用户实际看到的画面**（由 `client/src/pages/LeaderCandidates.tsx:243` 决定）：

```tsx
{backtestLoading ? «正在计算历史样本…»
  : !backtest || backtest.totalSamples === 0 ? «历史候选样本不足，暂无法计算回测结果。»
  : (...)}
```

即：回测端点 500 ⇒ `backtest` 为 `undefined` ⇒ 页面显示 **「历史候选样本不足，暂无法计算回测结果。」**
—— 这是**误导性文案**：真实原因是接口 500，不是样本不足。（历史明细表有 error 分支，会显示真实错误。）
`backtest` 的 `isError` **在本页没有任何分支**，这也是一处「静默失败」。

## 2. 因果链

```
①  21:40  有行情写入（.cache/stock-price-day-index.json 被更新 —— 该文件只在 upsertStockDailyPrices 后写）
②  21:54  .cache/leader-candidate-backtest/ 被清空
          （写入钩子 invalidateLeaderCandidateBacktestCaches() → clearLeaderCandidateBacktestSnapshotsSync()，db.ts:2159-2172）
③  22:01:30 dev server 重启（进程 pid 35036）⇒ 进程内 5 分钟 / 30 分钟结果缓存同时清空
④  22:08  用户打开 /leader-candidates ⇒ 内存缓存与磁盘快照"双空"⇒ 必须走冷算
⑤  冷算路径 loadBacktestBaseContext → loadBacktestPriceRows：
          临时表 + JOIN 拉取全区间 1,529,449 行 stock_daily_prices
⑥  该函数用 $client.promise().getConnection() 取**专用连接**（不做存活探测）
          ⇒ 抽到池内死连接 ⇒ 首条语句 `Connection lost`
⑦  withReadRetry 重试 3 次 —— 但 finally 里 conn.release() 把**同一条坏连接**放回池顶，
          下一次 getConnection() 又 pop() 到它（mysql2 空闲队列是 LIFO）
          ⇒ 3 次全落在同一条坏连接上 ⇒ 整轮作废 ⇒ tRPC 500
```

第 ⑥⑦ 步与项目既有记录完全吻合：`server/db.ts:182-190` 已写明「`getConnection()` 从
`_freeConnections` 直接 `pop()`、**不做存活探测/ping**」，2026-09-13 曾因死连接修过一次
（`maxIdle = poolSize - 1` 以恢复 idle 回收）。本次是**池内多条同时失效**的更彻底形态。

## 3. 决定性证据：同一条查询用全新连接 22.8 秒跑通

只读探针 `docs/evidence/_probe_lc_slowpath.mjs`（**新连接**，非池）实测：

| 区间 | 耗时 | 涨停信号日 | 合并区间数 | 取回价格行 | 传输量 |
|---|---|---|---|---|---|
| 最近 ~7 周 | 3,063 ms | 2,413 | 1,243 | 42,749 | 7.0 MB |
| 最近 ~3.5 月 | 2,925 ms | 6,094 | 2,633 | 105,418 | 17.2 MB |
| 2026 年内 | 4,033 ms | 12,646 | 5,125 | 207,975 | 34.0 MB |
| **全区间（dev server 实际走的）** | **22,827 ms** | **99,918** | **37,342** | **1,529,449** | **≈248 MB** |

其中全区间分解：`innerQuery=749ms` / `INSERT 37,342 区间=2,138ms` / `fetchAll(153 万行)=19,287ms`。

**推论**：

1. **链路不慢**：248 MB / 19.3 s ≈ **12.9 MB/s**。历史注释里的「196s 拉 152 万行」是旧条件下的数字，
   当前链路已快一个数量级 —— 所以「跨境带宽受限」这个假设**本次不成立**。
2. **查询不重**：37,342 条 `INSERT`（约 2 MB 单条语句）2.1 s 完成，说明「大 SQL」也不是本次的失败点。
3. **服务端不杀查询**：`@@max_execution_time = 1,800,000`（30 分钟）。
4. **网络没断**：`_probe_db_tcp.mjs` 显示 TCP 到 TiDB gateway 正常、`cloudflare/google/npm` 全 200；
   DNS 上 TiDB 走**真实公网 IP**（非 fake-IP），GitHub 才走 fake-IP（198.18.x.x）。
5. ⇒ 唯一剩下的解释就是 **dev server 进程内的池状态坏了**。

## 4. 方案（供选择，本轮未实施）

### P0 — 立刻恢复（**不改代码**，但会影响正在使用的页面，需你确认）

| 编号 | 动作 | 依据 / 风险 |
|---|---|---|
| **P0-1** | **重启 dev server**，重建连接池 | 池里死连接是唯一已证实的失败源；重启后 `getConnection()` 必得新连接。风险低。 |
| **P0-2** | 重启后**耐心等首次冷算跑完**（预计 25~45 s：248 MB 拉取 + 引擎计算） | 冷算成功即写入 `.cache/leader-candidate-backtest/*.json`（≈5.5 MB）⇒ 之后 6 h 内秒开。中途反复刷新没有意义（有单飞，不会更快）。 |
| **P0-3** | 冷算成功前**不要**点「回填历史行情」、不要跑行情同步 | 每次 `upsertStockDailyPrices` 都会触发快照清空，把页面打回冷算。 |

**若 P0-1 后仍 500**：说明坏连接不止池内一条，需走到 P1-1（而 P1 要动 `server/**`，按项目铁律
必须择时（避开你在用页面）并热重启、同时杀掉在途 Run）。

### P1 — 防复发（小改，改完需热重启）

| 编号 | 动作 | 收益 |
|---|---|---|
| **P1-1** | `loadBacktestPriceRows` 取到专用连接后先 `ping()`/`SELECT 1`，坏连接**直接销毁重取**（而不是 release 回池） | 直接消除 ⑥⑦ 两步的失败链；这是最小对症改动 |
| **P1-2** | 同一函数按**时间或股票分片**拉取（每片独立连接 + 独立重试，失败只重跑该片） | 实测每片 ≤4 s（年内 4 s）⇒ 单点失败不再作废整轮 305 s |
| **P1-3** | 快照改为「**标脏 + 后台重建 + 原子替换**」，数据写入时**不再直接删**快照 | 消灭「数据写入 ⇒ 页面一段时间完全不可用」这个窗口（6 h TTL 兜底，最多看到略旧数据） |
| **P1-4** | 服务启动后**后台异步预热**一次快照 | 把「重启 ⇒ 首访必冷算」变成「重启后台补缓存」 |

### P2 — 根治

| 编号 | 动作 | 说明 |
|---|---|---|
| **P2-1** | 把 T+1/T+2 溢价等统计**下推 SQL**，别把 153 万行（≈248 MB）搬到 Node | 这是冷算耗时与内存的大头 |
| **P2-2** | 建「策略专用窄表/物化窗口表」 | 在写入侧摊薄成本 |
| **P2-3** | 前端把「接口失败」与「样本不足」分开显示（并给 `backtest` 加 error 分支） | 现在 500 会被显示成「样本不足」，误导用户 |

1. **是否现在就执行 P0-1（重启 dev server）** —— 这是唯一能立刻恢复且已论证充分的手段。

3. P1-3（快照不再直接删）是否接受「写入后短时间可能看到略旧数据」的语义。
4. P2-3 的前端文案修正是否一并做（属 `client/**`，走 HMR，成本很低）。

## 6. 环境旁注（与本次故障无因果，但影响后续操作）

- 本仓库当前工作树有**大量并行改动**（`server/researchEngine/**`、`client/src/pages/research/ReportView.tsx`、
  `scripts/generateResearchReport.mts` 等，属另一条工作线）。**并行会话每次改 `server/**` 并重启，
  都会清空进程内缓存并重建池** —— 这与本故障的放大有关。建议：使用时段与改 server 的时段错开。
- 我的独立探针首次建连失败 3/3、约 4 分钟后再试即成功（1.7 s）：说明**短时间内反复新建连接会被对端拒绝 /
  复位**。探针脚本已内置建连重试（5 次、间隔 4 s）。
  另注：探针**不要**显式开 `compress`（`server/db.ts` 默认开 compress 是给池用的；独立连接上开启时，
  本机实测建连握手失败率明显更高）—— 这属于探针使用注意，不是产品缺陷。
