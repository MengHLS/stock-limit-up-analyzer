## 1. 问题定义

用户诉求（原话）：

1. 「量化回测-组合回测界面每次进来等待时间太久了」
2. 追问后明确：**「切换回测区间还是要等很久」**
3. 本轮目标：**「彻底解决这个冷却时间问题」**，且「明确切区间也尽量快速加载」。

症状分三级，严重程度递增：

| 级别 | 场景 | 表现 |
|---|---|---|
| L1 | 首次进入（服务刚重启 / 隔久了） | 等 21~58s 才出内容 |
| L2 | **切换回测区间** | 每次换区间必然重新等（数分钟） |
| L3 | **切到较宽区间（如「近2年」）** | **等 256.9s 后直接 500 失败** |

## 2. 实测数据（本文方案的唯一依据）

### 2.1 阶段耗时拆解（冷进程，脚本直调，区间 2025-09-01~2026-09-19）

| 阶段 | 耗时 | 备注 |
|---|---|---|
| `dailyPriceCoverage`（`stock_daily_prices` **8,895,704 行全表聚合**） | **18.24s** | 第 2 次 0.00s ⇒ 内存缓存命中；TTL 仅 10 分钟 |
| `marketFactorRows`（`limit_up_records` 全表 GROUP BY → 1,873 行） | **10.30s** | 第 2 次 0.00s ⇒ 已缓存；写入时被逐批清空 |
| `suspensionWindows`（全表 → 182 行） | **0.33s** | 🔴 **零缓存**，每次 base context 都重读 |
| `loadBacktestBaseContext` 1 年（17,324 records / **280,922 rawRows**） | **46.48s** | 5 路并行读；其中上两项当轮已预热 |
| `loadBacktestBaseContext` 2 年（34,030 records / **514,510 rawRows**） | **137.95s** | 同上 |
| `runLeaderCandidateEngineProbe`（**生产 Strategy Engine**） | **2.10s** | 910 笔成交 |
| 生产核心报表（`includeResearch:false`） | **1.80s** | |
| **研究段增量**（~140 次 research-legacy 模拟：12 滚动窗口 ×5、全周期 5 策略、5 因子消融） | **2.31s** | 🔴 远小于预期 |
| **计算合计** | **≈6.2s** | |

### 2.2 端到端（走真实 dev server 的 `sentiment.getLeaderCandidateResearch`）

| 场景 | 结果 |
|---|---|
| 1 年区间（= 页面默认值） | 200，**21.0s**（21:41 测）/ **57.9s**（22:19 测）⇒ 波动 **2.8×** |
| 2 年区间（= 点「近2年」） | 🔴 **500 `connect ETIMEDOUT`，等待 256.9s 后失败** |
| 1 年区间 `rawRows` 序列化体积 | **52.15MB**（JSON，长键，≈190B/行） |
| 结果 JSON 体积 | 9.84MB（未剥离明细） |

### 2.3 结论

🔴 **瓶颈完全不在计算，而在「取数」。**

- 全部计算（引擎 + 生产报表 + 整个研究段）只占 **≈6.2s**；而取数占 **46.5s（1 年）/ 138s（2 年）**。
- 取数成本 ≈ 线性正比于「候选股 × 涨停窗口」内的价格行数，跨境链路实测约 **3.7~6.2 千行/秒**。
- 这块数据**换区间就全部重拉**，且**永不落盘**（`backtestBaseContextCache` 是 15 分钟内存缓存、按区间字符串作键）⇒ 每次 dev 热重启、每次换区间，都要重新跨境搬运数十万到数百万行。
- 宽区间会撞穿跨境连接超时 ⇒ 不是「慢」，是**功能不可用**（L3）。
- ⚠️ 顺带纠正一个既有误判：**研究段（~140 次模拟）不是瓶颈**（仅 2.31s），此前把优化重心放在结果缓存/载荷上，方向偏了。

## 4. 方案（分三期，可独立回滚）

### P0 —— 把「与区间无关」的三块读盘化（改动最小、收益确定）

**做什么**：`dailyPriceCoverage`（18.2s）、`marketFactorRows`（10.3s）、`suspensionWindows`（0.33s，当前零缓存）三项加
**磁盘快照**（长 TTL）+ 由现有 `invalidateLeaderCandidateBacktestCaches()` 失效，复用既有 `server/leaderCandidateBacktestSnapshot.ts` 机制与其全部调用点。

**为什么有效**：这三项**只依赖数据内容、与回测区间无关**，却是每次冷启动的固定开销；dev 下 `tsx watch` 频繁重启会反复重付。
`dailyPriceCoverage` 的既有注释担心「清空会导致下一次重跑 9s 全表聚合」，磁盘快照正好消除这个两难。

**改动面**：`server/db.ts` 局部（两个 getter 包一层快照 + 一个 getter 增加缓存）。零语义变化、零 schema、零 migration。

**风险 / 反风险**：
- 低。但有**一处必须注意的既有约束**（否则实施时会踩）：
  🔴 `dailyPriceCoverage` 的内存缓存**被刻意排除在 `invalidateLeaderCandidateBacktestCaches()` 之外**（源码注释：写入路径是**逐批**调用的，逐批清空会把一次回填变成数十次 890 万行全表聚合）。
  ⇒ 因此**不能**简单地把这三项挂到"写入即清空"的钩子上，正确做法是**「快照自带数据戳 + 读时比对」**：
  读取时若 `readBacktestDataStamp()`（3 个带索引 `MAX()`，≈214ms，15s 备忘）与快照记录的不一致 ⇒ 视为未命中并重算，否则直接返回。
  这样既拿到正确性（外部脚本回填也能被 15s 内发现），又不会在批量写入期间反复触发全表聚合。
- 快照体积：coverage 是小结构体、marketFactor 1,873 行、suspension 182 行 ⇒ **远小于 `LEADER_CANDIDATE_BACKTEST_SNAPSHOT_MIN_BYTES`（256KB）阈值**，需为该层单独放低阈值，或改用独立的小对象缓存文件（不要为了复用而强行塞进现有快照模块）。

**验收**：热重启后首次调用三项合计 ≤0.5s；写入数据后 ≤15s 内反映新值（G6 不破）。

**预估**：冷启动 −28s。

### P1 —— 价格行本地镜像（**「彻底解决」落点**）

**做什么**：把 `loadBacktestPriceRows` 从「每次跨境 JOIN」改成 **「本地优先、缺口回源」**。

**设计要点**：
1. **存储粒度必须到「(股票, 日期) 行级」**，不能按区间做快照 —— 否则换区间仍要重拉（这是 P1 与此前「按区间快照」方案的本质区别）。
2. **格式**：固定宽度二进制或短键 NDJSON。JSON 长键 190B/行不可接受；二进制约 40B/行
   ⇒ 1 年 28 万行 ≈ 11MB、2 年 51.5 万行 ≈ 21MB、覆盖全部候选历史窗口估计 **60~150MB**。
3. **覆盖索引**：维护 `stockCode → 已覆盖日期区间 + 写入时的远端标记`。查询时先算覆盖率：
   全命中 ⇒ **纯本地读**（预计 1~3s）；有缺口 ⇒ 只把缺口日期下推到远端。
4. **失效策略（三层）**：
   - 粗粒度：`readBacktestDataStamp()` 变化 ⇒ 全量校验；
   - 中粒度：某股远端最新交易日**回退**（修订/删除）⇒ 保守判定该股本地片段可能过期 ⇒ 只重拉该股；
   - 细粒度：允许配置「强制冷拉」开关（`FORCE_REMOTE_PRICE=1`）。
5. **交付工具**：一个只读校验脚本，支持「同区间 A/B：本地读 vs 直连远端」，逐字段比 `rawRows`（含 `preClosePrice` 等全部 8 个字段）并比结果指纹。

**为什么有效**：把 46.5s / 138s 的跨境传输换成一次性成本；此后任意区间（含从未访问过的新组合）都只读本地。

**改动面**：新增本地价格库模块 + `loadBacktestPriceRows` 改造 + 校验脚本。**不改变任何评分/模拟逻辑**。

**风险 / 反风险**：
- ⚠️ **中高**。最大风险是「本地副本与远端不一致」⇒ 静默算出不同结果。
- 反风险：本项目既有硬口径「改写价格取数**必须 A/B 逐字段对比后才可改**」—— 必须把该 A/B 做成 P1 的**准入门槛**（不通过就不合并），并在页面上保留「数据来源 = 本地镜像 / 远端」的可观测标记（仅诊断，不给用户看）。
- 回滚：本地库是纯旁路缓存，删目录 + 关开关即回到现状，零不可逆操作。

**验收**：G2（2 年 ≤10s 且不报错）、G3、G5（A/B 逐字段 100% 一致）。

**预估**：切区间从数分钟/超时 ⇒ **数秒**。

---

### P2 —— 体验层：让「切区间」不再自动触发重算（纯前端，零服务端风险）

**做什么**（`client/src/pages/Backtest.tsx`）：
1. 区间与参数编辑只改**草稿态**；新增显式**「开始回测」**按钮 —— 只有点它才发请求（现在是改一下就自动重算）。
2. 界面明确回显**「当前显示结果对应区间 X ~ Y」**，避免草稿与实际结果混淆。
3. `staleTime` 与 `gcTime` 对齐（默认 `gcTime`=5min 会让 30 分钟内回来也重拉）。

**为什么有效**：把「等待」从**隐式**变成**显式且可控** —— 切区间本身 0 等待（G3 立刻达成），用户只在真正要算时才等一次。
即使 P1 尚未落地，仅此一项也能消除「随便点一下区间就开始等 4 分钟」的体感灾难。

**风险**：低（纯前端、可单独回滚）。唯一需要产品判断的是交互形态变化 ⇒ **需你确认**（见 §6 决策点）。

## 5. 明确不做的事（避免再次跑偏）

| 不做 | 原因 |
|---|---|
| 研究段并行化（worker_threads） | 计算只占 2.31s，收益 <1s，纯增复杂度 |
| 分段端点（总览先出、重页签懒加载） | 同上；且要动研究报表形状（`rollingWindows` 等），风险与收益不成比例 |
| 结果载荷裁剪（剥离 `historicalRows`、裁 `rollingWindows` 死重 2.4MB） | 只影响传输体积（1~2s 量级），**与冷算无关**；本轮已实测其在 1 年区间只省 10% |
| 换数据库 / 换云区域 | 属基础设施决策，成本远高于 P1，且不能解决「重复拉同一批数据」的根本浪费 |

## 6. 需要你确认的决策点

| # | 决策 | 选项 |
|---|---|---|
| D1 | 交互形态是否改 | **A. 改**（加「开始回测」按钮，切区间零等待）／ B. 不改，保持「改参数即重算」，只靠 P0+P1 提速 |
| D2 | P1 的落地范围 | **A. 只按需懒加载**（首次访问某股才缓存，磁盘占用随使用增长）／ B. 一次性预热全部候选历史窗口（约 60~150MB，换取全部区间首次就快） |
| D3 | 实施顺序 | **A. P0 + P2 先上，观察后再做 P1**（推荐）／ B. P0 → P1 → P2（先拿根治，再改交互）／ C. 只做 P1 |

## 7. 建议

**推荐 D1=A、D2=A、D3=A**，理由：

- **P0** 收益确定、改动最小、零语义变化，先吃下 28s；
- **P2** 是唯一能立刻让「切区间」变成 0 等待的动作，且纯前端可独立回滚 —— 用户主诉当天即解；
- **P1** 才是「彻底」，但它会引入一份需要长期看守的本地副本（一致性风险中高），值得在 P0/P2 落地、痛点已缓解的前提下**从容做**，并强制以「A/B 逐字段一致」为准入门槛；
- L3（宽区间 500）**必须由 P1 解决**（P0/P2 都不够）⇒ 若你希望尽快消掉这个功能不可用，可把 P1 提前到与 P0 并行。
