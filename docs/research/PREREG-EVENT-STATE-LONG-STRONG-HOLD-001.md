## 1. 唯一问题

**在 Event-State Long 的冻结配置上，把「持有满 40 个交易日后退出」改为「若第 40 个持有日仍强势则延长到第 60 日」，是否产生正的增量？**

## 2. 🔴 结构性约束（本实验设计的根据）

`strongHold` 只能声明在 `ExitPolicyDefinition` 内，而
`server/research/exitPolicyCommon.ts#exitPolicyDefinitionErrors`（L376-383）**强制要求 `policy.stop` 是对象**。

⇒ **无法表达「无止损 + 强势续持」**。因此本实验**必然**同时引入止损，**必须**用一条
「只加止损、不加强势续持」的臂把止损效应隔离出来 —— 否则 B−A 的差异会把止损与强势续持混在一起。

## 6. 判据（事前声明）

1. **主判据**：`canonicalMetrics.totalReturnPct`（B vs C）；同时报 `maxDrawdownPct`（正数幅度）、
   `cagrPct`、`sharpeRatio` / `sortinoRatio` / `calmarRatio`（252 日、rf=0）。
2. **纯增量**：`B − C` = 强势续持的增量；`C − A` = 止损的增量。**两者必须分开报**。
3. 🔴 **必须同时披露延长持仓的资金占用代价**（项目既有教训：只报延长带来的直接盈亏会**系统性高估**）：
   延长持有会占用 `1/180` 的仓位槽并挤掉后续候选 ⇒ 需报「被挤掉的成交数」与
   「延长交易 vs 被替代交易的净额」，而不是只报延长交易自身的盈亏。
4. **交易集合变化**：成交笔数、胜率、盈亏比、平均持有天数、出场原因分布（止损 / 时间退出 /
   延长后时间退出）。
5. **年度符号一致性**：逐年 `totalReturnPct` 的符号（避免单一年份主导）。
6. **判定口径**：只有 `B − C > 0` **且** 年度符号多数一致 **且** 资金占用代价已披露，
   才可称「强势续持有正增量」；否则如实报「无正增量 / 不确定」。
   **收益不好不是中止理由，但也不得因此放宽判据或加臂。**

### 11.1 执行中发现并修复的两个**自身**缺陷

1. **臂文档丢了 `exit.candidateExitPolicy="DISABLED"`**（严重）。
   初版补丁写成 `{ definition: { ...parent, exit: { rules } } }` ⇒ **整个 `exit` 被替换** ⇒
   冻结值 `candidateExitPolicy="DISABLED"` 丢失 ⇒ 平台回落「候选退出」默认行为。
   **实测后果**（错误的 `3.0.0`）：4537/4825 笔以「候选退出」离场、平均持有 **2.97 天**
   （控制臂 41.01 天）⇒ 该臂**不再是「只加止损」**，单变量假设被破坏。
   **修法**：只替换 `exit.rules`，保留 `exit` 其余兄弟字段；并**新增自检** `frozenUnchanged.exitSiblings`
   + 回显 `candidateExitPolicy`。修后两臂均为 `"DISABLED"`、`exitSiblings = true`。
   **版本处置**：`3.0.0` / `4.0.0` 内容不完整且**版本不可变**（I-5）⇒ 修正臂落到**未占用**版本号
   **`5.0.0`（C′）/ `6.0.0`（B′）**，内容严格派生自有效基座 `2.0.0`；`3.0.0` / `4.0.0` **登记为无效/被取代**
   （未删除、未修改其内容）。

2. **执行尾窗派生不认「统一 policy」形式**（阻塞级）。
   `assemble.ts#resolveEventWindowExitTailTradingDays` 的便宜筛选只认
   `rule.thresholdUnit === "TRADING_DAY"`，而带 `policy` 的规则**不得**声明 `thresholdUnit`
   （`definitionValidation.ts` 禁止两者并存）⇒ policy 形式静默拿到**尾窗 0** ⇒ 退回物化路径 ⇒
   区间超出数据集事件窗时被守卫拒绝（实测 C 臂报
   `实验日期范围 [2019-01-03, 2026-01-28] 超出数据集窗口 [2019-01-02, 2025-09-26]`）。
   **修法**：① 便宜筛选同时认 `rule.policy.timeExit.kind === "FIXED_HOLDING_DAYS"`；
   ② 尾窗改按**有效最长持有期**派生 = `max(timeExit.holdingDays, strongHold.extendToHoldingDays,
   strongHold.runnerExitAtHoldingDays ?? 0)` + 顺延缓冲 20。
   新增回归测试 3 例（policy 形式 = rule-list 等价；strongHold 40→60 ⇒ 80；取较大者 + `enabled=false` ⇒ 0），
   `eventWindowExecutionTail.test.ts` **10/10 通过**。

### 11.4 🔴 臂 B′（强势续持）当前被**环境/覆盖上限**阻塞（未完成）

- 现象：`4.0.0`（旧 B）失败 2 次、`6.0.0`（B′）失败 1 次，**共 3/3 全部失败**，
  均为 `ECONNRESET`（`errno −4077`，即 ROADMAP `9cn` 记录的池化连接被掐断形态），
  发生在**数据集构建**阶段（`index_daily` / `liquidity_daily`）。
- 对照：**所有尾窗 = 60 的运行（A、C、C′）全部成功**；只有 B/B′ 的**尾窗 = 80** 失败
  ⇒ 不是随机抖动，而是与**读取规模**相关。
- 根因判断：§11.1-② 的修法让 B′ 的尾窗 = `max(40, 60) + 20 = 80` ⇒ 覆盖到
  `rd = 15 + 1 + 80 = 96`，**超出该数据集自己声明的后置窗口 `postWindowDays = 80`**
  ⇒ 读取量显著变大 ⇒ 触发连接掐断。
- **下一步（尚未实施）**：把派生尾窗**封顶在数据集自己声明的 `postWindowDays` 之内**
  （对 B′：尾窗 `min(80, 80 − 15 − 1) = 64` ⇒ 覆盖恰好到 `rd = 80`，仍完整覆盖
  第 60 日延长的次日开盘成交 `rd = 76`，并留 4 日顺延余量）。这是**平台覆盖口径**的收口，
  **不是**实验参数调整（`strongHold` 阈值/延长期**不动**）。
- 该封顶需要把数据集的 `postWindowDays` 接到尾窗派生或游标构建处，属**最小契约补齐**；
  实施前须补回归测试并复核对其他策略的影响（既有尾窗 60 的策略不受影响：`16+60=76 ≤ 80`）。

### 11.9 执行尾窗夹取（本实验解锁 B″ 的最小平台修复）

- **现象**：B″ 的派生尾窗 = `max(40,60)+20 = 80` ⇒ 需 `rd ≤ 96`，而 `780004` 的 post 上限为 **rd=80**。
  平台在 `datasetFromRegistry.ts` 对超限是**响亮拒绝**的（`REGISTRY_POST_WINDOW_TOO_SHORT`，
  注释写明「🔴 不静默夹取窗口」）⇒ 流式路径抛错 → **回落重建路径** → 在重建阶段被连接掐断
  （`ECONNRESET`，3/3 次；这才是前几轮「B 失败」的真实根因）。
- **修复**：新增纯函数 `assemble.ts#clampEventWindowExitTailTradingDays(derived, end, postMax)`，
  把**派生值本身**夹到数据集能提供的范围内（`可用尾窗 = postMax − end − 1`），
  并在装配摘要新增 **`eventWindowExitTailTradingDaysClampedFrom`** ⇒ **夹取前后都可见（不静默）**。
  未改 `datasetFromRegistry.ts` 的任何守卫（平台「不静默夹取」的原则保持不变）。
- **效果**：B″ 尾窗 80 → **64** ⇒ 覆盖恰好到 `rd = 80`，仍**完整覆盖**第 60 日延长的次日开盘成交
  （`rd = 76`）并留 4 日顺延余量；B″ 一次跑通。
- **影响面**：仅影响「派生尾窗 > 数据集 post 上限」的策略。既有尾窗 60 的策略（`16+60=76 ≤ 80`）
  **不受影响**；`post 上限读取失败` ⇒ 不夹取（保持既有行为，不把失败当 0）。
  新增回归测试 5 例，`tests/server/runWorkbenchAssembly` **13 文件 / 96 例全绿**。
