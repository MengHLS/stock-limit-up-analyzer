## 2. 五个任务块的规格

每块的统一结构：**主方案（必选） + 子方案（可选，默认继承） + 参数（折叠）**。

### ① 选股
| 项 | 内容 |
|---|---|
| 回答 | 买什么样的股票？ |
| 主方案 | 一组**完整选股方案**（事件 + 观察窗 + 触发 + 配方），例：`首板回踩 · 3F 评分取前 3` |
| 子方案 | `排除一字板/T字板`、`观察窗内需回踩`（对应 3570001 的 `requirePullback` / `excludeEventDayOpenAtLimit`） |
| 参数 | 主方案暴露的：`取前几名`、`最大振幅上限` 等（默认可直接跑） |
| 现状 | **RECIPE 预设 11 个已就绪**（服务端注册表，中文名已就位）；事件/窗口/触发/条件的方案化**待补** |

### ② 出场
| 项 | 内容 |
|---|---|
| 回答 | 什么时候卖？ |
| 主方案 | 完整退出政策，例：`6%止损｜8%回撤保护｜破均线走｜最长20日`（= `EXIT_POLICY` 组合预设） |
| 子方案 | `创新高延长至 20 日`（= `RUNNER_BRIDGE`）；还可逐子槽覆盖（止损/止盈/到期/续持） |
| 参数 | 止损比例、回撤幅度、均线窗口、持有日、Runner 状态…（中文名 + `= 6%` / `= 5 个交易日`） |
| 现状 | ✅ **已完备**：`EXIT_BASE` 46 个基座 + 组合 6 个 + 原子槽 5 组 |

### ③ 仓位（原「仓位与风控」；风控字段已按裁定删除编辑面，见 §5）
| 项 | 内容 |
|---|---|
| 回答 | 每笔买多少 / 最多同时持有几只 |
| 主方案 | 例：`固定比例 20% × 最多 5 只`、`等权 N 只`、`固定金额` |
| 参数 | 单笔比例 / 固定金额、**最大同时持仓数**（唯一编辑点，双写两处；见 §5.4） |
| 现状 | ❌ **无预设**（`PositionSizingEditor.tsx` 无 preset 概念）⇒ 需新建预设族 |
| ⚠️ | **不再包含风控**：`risk.*` 与 `position.maxExposure` / `maxSinglePosition` 执行层零实现 ⇒ 按裁定**删除编辑面**，只在「技术细节」只读展示（§5.2） |

### ④ 成本与成交
| 项 | 内容 |
|---|---|
| 回答 | 怎么成交 / 花多少成本 |
| 主方案 | 例：`A股标准（20.2bp）· 100万 · T+1 开盘` |
| 参数 | 初始资金、佣金/印花/过户/滑点、每手股数、最低佣金 |
| 现状 | ⚠️ **零散存在**：策略定义页 CostFields 有"一键预设"；研究草图侧 `candidateSketchCostPreset.ts` 是**客户端 + localStorage**，未进服务端注册表 |

### ⑤ 可调参数（用于参数搜索）——**不是配置块，是派生视图**
| 项 | 内容 |
|---|---|
| 回答 | 上面四块里，哪些参数允许被搜索？范围多少？ |
| 形态 | **从 ①–④ 的参数里勾选** + 给 min/max（或候选集） |

## 3. 信任层（本方案的一等公民）

五块各自独立选方案 ⇒ 组合数达数百量级，**其中绝大多数从未被验证**。页首必须始终回答："**这还是被验证过的那套吗？**"

| 状态 | 判定 | 界面 | 后续动作 |
|---|---|---|---|
| 🟢 **一致** | 组合命中某个已验证版本 **且**所有参数等于该版本默认值 | 「与已评估版本 `3570001` 完全一致」+ 链到该版本的评估 / 模拟盘 | 无 |
| 🟡 **变体** | 组合命中，但有参数被改 | 「`3570001` 的变体 · 参数已改 **3** 项」+ 列出改了哪几项 | 「还原为已验证版本」/「重新评估」 |
| ⚪ **全新** | 组合未命中任何已验证版本 | 「全新组合 · 尚未验证」 | 「跑一次回测」 |

**判定依据**（唯一口径，不在前端自造）：
- **参数是否被改**：逐项与所选方案的 `defaultValue` 比对（当前 `PresetSelection.parameters` 已带默认值，可直接比）。
- **组合是否命中已验证版本**：由后端给"已验证指纹"清单（策略版本的 `definition` + `recipe` 指纹），前端只做**相等判断**，不做语义推断。

> 这一层是**量化平台与选股工具（Composer 等）最本质的区别**：我们的数字带"验证状态"，改了参数就不再算数，必须让用户看见。

## 4. 三条硬约束

| # | 约束 | 为什么 |
|---|---|---|
| **C-1** | **⑤ 只做派生视图**：只勾选 + 范围，不引入自己的方案 | 否则同一参数在两处定义（双真相） |

### 5.2 删除的落法：**只删编辑面，不删数据面**（硬约束，不可简化）

| 层 | 动作 | 理由 |
|---|---|---|
| **前端「③」块** | **删除**这些字段的编辑控件 | 这正是"假旋钮"的来源 |
| **前端「技术细节」** | **保留只读展示** + 标注「仅声明，不参与回测」 | 值是真实存在的；藏起来 = 隐瞒。且 golden diff / 等价判定需要它们 |
| **research schema / validator** | **保留**（继续接受与校验既有值） | 🔴 既有文档里就有这些键（`maxSinglePosition` 出现在 **174/176** 个版本里）；删 schema 会让"加载→保存"派生出不同的 v1 视图 ⇒ **指纹变化 ⇒ 版本不可变闸门拒绝保存** |
| **strategyCore `RiskSpec`** | **保留** | 🔴 `server/strategyCore/definition.ts:198 normalizeRiskSpec()` 是**白名单归一化**（只保留 7 个键）——从 core 删字段 = **主动丢弃**既有值，直接违反"既有策略零改写" |
| **执行层** | 不动（本来就没有实现） | 本次**不接线** |

> 一句话：**"删除" = 从用户能拧的旋钮里删掉，不是从数据里抹掉。**

| 层 | 现在认哪个 |

> - **I-10** 的方向按「多数字段必填 ⇒ 只标可选」：本页 7 段里必填的占多数，逐项盖「必填」章只会制造噪音（NN/g 的原意正是「标少数派」）。因此 `Field` 只提供 `optional`；红色「必填未填」与段缺口胶囊继续承担必填表达。
