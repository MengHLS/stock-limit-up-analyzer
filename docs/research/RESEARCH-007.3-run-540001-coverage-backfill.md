## 4. 执行方式：为什么是 `runIncremental` 而不是 `runEngine`

读源码确认的分工（`server/researchEngineRouter.ts:457-490`、`server/researchEngine/engine.ts:400-410`）：

| | `runEngine`（整轮） | `runIncremental`（补跑） |
|---|---|---|
| 覆盖范围 | 该 Run **全部**分析的结果 | 只补「尚无有效结果」的（PENDING/FAILED/CANCELLED） |
| 是否重写已完成结果 | **会覆盖** | **不覆盖**已 COMPLETED 的 |
| 基准 | 当前配置 | **Run 冻结快照**（Dataset Version + 日期窗口）⇒ 新旧可比 |
| 结论 | 生成 | **不生成**（`conclusionId` 恒为 `null`） |

选 `runIncremental` 的理由：**已有 135 条结果的数字一字不动**，新增 45 条按同一快照补算。

代价（如实登记）：**本批次不生成结论**，Run 540001 的结论仍是原有的 `480001 REJECTED`。
引擎给出的确切口径：

> `INCREMENTAL_EXECUTION: 增量批次只补算部分分析。结论需要**该 Run 全部分析**的摘要，
> 而 AnalysisSummary 是执行期产物、未落库，无法重建已跳过分析的历史摘要。因此本批次不生成结论，
> 并保留既有结论不动（其证据未被改写）。如需产出反映全部分析的新结论，请新建 Run 或整轮重跑。`

## 8. 仍然不能实现的（明确列出）

| 需求 | 能否 | 原因 / 出路 |

| 加资格口径 × T+1~T+4（120 条） | ❌ | 变量层只有 `holds_event_low_{5,10,20}d`，**无 1d~4d**；`EVENT_LOW_GUARD_BASES` 无 `"open"`。最小扩展 = 视界收窄到 `pathHorizons ∩ [1,5]` + bases 加 `"open"`，须改 `server/researchEngine/variables.ts`（**会热重启杀在途 Run**） |

| 格间两两检验（相邻桶差） | ❌ | 落库只有「条件组 vs 全样本」；前端硬造会成为**不可验证的新统计量**，故意不做 |
