## D. 三个杠杆的实测（同一时间窗、受控）

数据集 **v2 = 390002**（23,978 事件 / 1,071,266 行），采样 3 批 = **270,000 行**，
`PERF_PROFILE=analyses`（13 特征 + 95 结果，即**全变量目录的最坏情况**），列投影守卫关闭（排除守卫开销）。

| 配置 | 耗时 | 吞吐 | 相对基线 | 该档贡献 |
|---|---|---|---|---|
| `raw / 不裁剪 / conc=1`（**生产现状**） | 267,478ms | 1,009 行/s | 1.00× | — |
| `compress / 不裁剪 / conc=1` | 73,494ms | 3,674 行/s | **3.64×** | 压缩 **3.64×** |
| `compress / 裁剪 / conc=1` | 63,586ms | 4,246 行/s | **4.21×** | 裁剪 **1.16×** |

| `compress / 裁剪 / conc=6` | 15,486ms | 17,435 行/s | 17.27× | 与 3 无显著差异 |

### 全量实测（12 批 / 1,071,266 行）

| 配置 | 实测 | 说明 |
|---|---|---|
| `compress / 裁剪 / conc=3` | **71,989ms ≈ 72s** | **改造后真实全量耗时（最坏情况）** |
| `compress / 不裁剪 / conc=3` | 107,838ms | 隔离出「裁剪」在全量下的贡献 = **1.50×** |
| `raw / 不裁剪 / conc=1` | ≈1,060s（外推） | 成本对行数严格线性（4× 数据 = 4.04× 时间，已实测），故由 267.5s × 3.97 外推 |

### 全量实测（验收场景：turnover → future_return_5d，12 批 / 47,835 行）

| 配置 | 实测 | 吞吐 |
|---|---|---|
| `raw / 不裁剪 / conc=1` | 95,961ms | 498 行/s |
| `compress / 裁剪 / conc=3` | **8,093ms** | 5,911 行/s |
| **提速** | **11.86×** | |

**注意这两个场景的主导杠杆完全不同，这解释了为什么倍数不一样：**

| 场景 | 每批行数 | 瓶颈 | 主导杠杆 |
|---|---|---|---|
| 全变量目录 | ~90,000 | **吞吐**（大查询由字节数主导） | **压缩 3.64×** > 流水线 4.09× > 裁剪 1.16× |
| 验收场景 | ~4,000 | **延迟**（每批 4 条小查询，RTT 与查询启动开销主导） | **流水线**（把 48 次往返的等待重叠起来） |

⇒ 变量集越小，流水线越关键；变量集越大，压缩越关键。三项都做，才能同时覆盖两类研究。

### ⚠️ 诚实边界（必须与数字一起读）

1. **跨日绝对数字不可比**。历史记录的 529.7s 采集于链路明显更快的时段
   （隐含吞吐 2,040 行/s，而今日「不裁剪不压缩」基线只有 1,009 行/s）。
   **可靠的结论是同一时间窗内的比值 ~17×**，而不是「529s → 72s」这种跨日拼接。
2. **裁剪的收益低于诊断期估计**。诊断期单查 prefix 得 3.27×，本轮混合装配里只有 1.16×~1.50×。
   原因：装配每批是 prefix/path/outcome **三条并发查询**，prefix 的收益被 path（单行最贵）稀释；
   且 path 的 `IN (2000 eventId) × relativeDay IN (20)` 大量时间花在 TiDB 执行侧的索引寻址，
   而非传输字节。**已用全量对照（107.8s vs 72.0s）独立复核过这一档，不是估算。**
3. **并发深度 3 与 6 无显著差异**（15,563 vs 15,486ms）。默认取 **3**：
   稳态最多 ~9 条语句在飞（3 批 × 3 条批量查询），在连接池 16 内留有余量，
   且内存峰值更低（每批 90,000 行 × 深度 3 vs 深度 6）。

## E. 列裁剪怎么做到「不可能静默变 null」

裁剪最危险的失败模式：少查一列 → `variables.ts` 的 `resolve` 普遍以 `?? null` 收口 →
**不报错**，只让某个特征悄悄变成一堆 null，在结果层几乎不可见。

因此**不要求任何变量手写「我用到哪些列」**，而是让**读取行为本身成为声明**：

| 防线 | 机制 | 拦什么 |
|---|---|---|
| ① 自动派生 | 「记录访问」代理跑一遍每个 `resolve`，读过哪些列就取哪些列（`deriveColumnProjection`） | 变量定义改动后投影**自动跟随**，不可能漂移 |
| ② 越界即失败 | 真实数据上把「读了未投影的列」变成 `PROJECTION_MISSING_COLUMN`（默认守卫首批） | 「只在特定取值下才走到的隐藏分支」 |
| ③ 差分测试 | 逐变量比对「全列取值」与「投影后取值」必须逐位相等；端到端比对 `columnProjection:"all"` 与派生装配的 `samples` | 任何口径改变都会让测试失败 |

派生结果（`PERF_PROFILE=analyses`，即全变量目录）：

| 表 | 全列 | 投影 | 实际取用列 |
|---|---|---|---|
| `event` | 18 | 12 | 结构列 + turnover / previousClose / limitUpPrice / daysSincePreviousLimit / historicalLimitCount / marketCap / floatMarketCap / boardType / market / industryCode |
| `prefix` | 13 | **5** | `datasetVersionId, eventId, relativeDay, close, volume` |
| `path` | 15 | **7** | 结构列 + `high/low/closeFromEventClose, pullbackFromEventHigh` |
| `outcome` | 10 | **8** | 结构列 + `maxReturn, minReturn, maxDrawdown, isBreakout, daysToBreakout` |

被丢掉的宽列（prefix 的 `open/high/low/amount/symbol/tradeDate/id/createdAt`；
path 的 `volumeRatio/breakoutPrice/symbol/tradeDate`）**没有任何变量读它们** ——
若将来有变量要读，派生会自动带上；若某变量在特定取值下才读，守卫会抛错。

## F. 流水线并发：为什么不是「并发分页」

事件分页链**必须串行**（下一页 cursor 依赖上一页）。因此本实现的并发不是「同时拉多页事件」，
而是把**批与批之间的取数与装配重叠**：

```
串行（原实现）： [事件页1][prefix∥path∥outcome 1][装配1][事件页2][…2][装配2] …
                  ↑ 装配期间链路完全空转
流水线（现在）： [事件页1][  数据1  ]
                       [事件页2][  数据2  ]        ← 数据在飞时下一批已开始
                            [事件页3][  数据3  ]
                 [装配1][装配2][装配3]             ← 消费端严格按批序
```

- **有界**：`pending` 里最多 `depth` 批，深度上限 16（env `RESEARCH_ASSEMBLY_CONCURRENCY`）。
- **保序**：消费端严格 `shift()` 顺序装配，实测**并发 1 与 4 的输出 `samples` 逐位相等**（有测试）。
- **快速失败**：任一子任务抛错立即向外抛，并把在飞批次 `Promise.allSettled` 收敛，不留未处理 rejection。

## G. 顺带补掉的 robustness 缺口：跨境读的瞬时重试

**问题**（本轮实测发现）：跨境链路偶发 `ECONNRESET`——14 次基准运行中出现 **1 次**，
发生在一条 40,000 行的 path 查询上。装配是「12 批 × 3 条大查询 = 36 次往返」的长任务，
**一次瞬时重置会让整轮装配作废**（用户已等数十秒到数分钟），代价与「慢」等价。

**方案**（`readRetry.ts`）：只读操作的有界重试。

- **只重试瞬时错误**：`ECONNRESET` / `ETIMEDOUT` / `EPIPE` / `PROTOCOL_CONNECTION_LOST` 等；
  **语义错误（表不存在 / SQL 非法 / 被取消）一律原样抛出**，不把真实缺陷伪装成链路抖动。
- **沿 `cause` 链判定**：Drizzle 把真实原因包在 `cause` 里，只看外层 message 会漏判。
- **有界**：默认 3 次尝试、退避 300ms → 900ms（额外等待 ≤ 1.2s）。
- **不静默**：每次重试都打告警，重试次数因此可观测。
- **不用于写路径**（写重试可能造成重复写入）。
